# Обновления и фоновые задания

В разделе **Обновления** доступны Talos upgrade, Kubernetes upgrade
и rolling reboot. Журнал и результаты доступны в разделе **Задания**.
Доступ к обоим разделам требует входа администратора.
Сначала выберите кластер в верхней части меню. Все операции, конфигурации,
логи и задания относятся к выбранному кластеру. Переключение кластера
или закрытие вкладки не отменяет уже запущенное задание.

## Запуск

1. Выберите операцию и целевую стабильную версию, например `1.14.1`.
2. Выполните **Проверить план**. Сервер проверит доступ к API, здоровье,
   состав нод, etcd, совместимость версий и installer.
3. Проверьте список нод и installer images. Для единственной control plane
   при её перезагрузке требуется подтверждение простоя API.
4. Нажмите **Запустить задание** и введите имя кластера.
5. Следите за шагами в журнале. Закрытие вкладки не отменяет работу backend.

Сервер повторяет проверки перед выполнением и создаёт проверенный снимок etcd.
Понижение версий и пропуск minor-версий отключены. Для Talos меняется тег
настроенного installer, с сохранением его репозитория и schematic.
Digest-only и неоднозначные installer references не принимаются.
Фактический schematic установленной системы сверяется с installer; при
несовпадении обновление блокируется, чтобы не потерять расширения.

Talos обновляется по одной ноде, сначала control plane; rolling reboot
начинается с workers. Kubernetes обновляется штатным `talosctl upgrade-k8s`,
с предварительным dry-run. Прогресс штатной команды сохраняется в журнале.
Завершение проверяется отдельно от отправки команды.

## Остановка и перезапуск

**Остановить после шага** запрещает начало следующих шагов. Эта кнопка
не отменяет команду, уже отправленную в Talos/Kubernetes.

После перезапуска backend незавершённое задание помечается `interrupted`.
Автоматического повторного выполнения нет: команда на ноде могла выполниться.
Проверьте версии, здоровье и maintenance-состояние нод, затем подтвердите
проверку в журнале. Подтверждение снимает блокировку, но не возобновляет задание.

Обновление можно снова запланировать по фактическому состоянию кластера.
Ноды с целевой версией пропускаются. Если нода осталась cordoned или unhealthy,
сначала необходимо восстановить её состояние; повторный preflight это проверяет.

## Размещение панели

При drain/reboot ноды, на которой работает TalosDeck, сам backend может быть
остановлен. Для непрерывного выполнения кластерных операций используйте
отдельную машину или management-кластер. Резервная копия на PVC внутри
повреждённого кластера может оказаться недоступной при аварии.

## Хранилище и зависимости

- Журнал: `./data/jobs`, переопределяется `TALOSDECK_JOBS_DIR`.
- Каталог должен сохраняться между перезапусками и быть доступен на запись.
- Поддерживается один процесс-исполнитель; файловая блокировка защищает
  каталог от одновременного открытия другим процессом.
- Одно фоновое изменение кластера за раз. Конфликтующие синхронные действия
  с нодами, бэкапами и Proxmox блокируются на время задания.
- Для локального запуска требуется `talosctl v1.14.0` в PATH либо путь
  через `TALOSDECK_TALOSCTL`. В Docker-образ он включён.
- Журнал ограничен последними 100 заданиями и 2000 событиями на задание.

## MachineConfig

В разделе **Конфигурация** выберите ноду и задайте patch. Поддерживаются
strategic merge и JSON6902. Для Talos 1.14 пример изменения метки ноды:

```yaml
apiVersion: v1alpha1
kind: KubeNodeConfig
labels:
  environment: staging
```

Проверка включает валидацию SDK и dry-run на самой ноде. Перед применением
показывается diff без секретов, содержимого файлов и встроенных manifests.
Подтверждение требует адрес ноды. Режимы: `auto`, `reboot`, `staged`.
`staged` означает сохранение до следующей перезагрузки, а не активную конфигурацию.

План действует 30 минут и перестаёт быть применимым, если текущая конфигурация
изменилась. Применение создаёт задание. История и исходные конфигурации
хранятся зашифрованными; HTTP выдаёт только очищенные версии. Первая проверка
сохраняет исходную ревизию. Восстановление также требует нового preview,
подтверждения и задания. История доступна, даже когда нода недоступна.

## API

Все запросы требуют авторизации администратора.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/jobs` | Список заданий |
| POST | `/api/jobs/plan` | Предварительная проверка |
| POST | `/api/jobs` | Создать задание |
| GET | `/api/jobs/:id` | Состояние и события |
| POST | `/api/jobs/:id/stop` | Остановить после текущего шага |
| POST | `/api/jobs/:id/acknowledge` | Подтвердить проверку прерванного задания |

В multi-cluster API замените `/api` на `/api/clusters/:clusterId`.
Непрефиксованные инфраструктурные маршруты оставлены только для автоматически
перенесённого старого кластера; для новых подключений используйте явный ID.
Auth остаётся общим: `/api/auth/login`, `/api/auth/me`, `/api/auth/logout`.

Дополнительные маршруты:

| Метод | Путь | Назначение |
|---|---|---|
| GET / POST | `/api/clusters` | Список / импорт |
| GET | `/api/clusters/:clusterId/jobs/:id/export` | Очищенный журнал JSON |
| POST | `/api/clusters/:clusterId/config/:node/plan` | Проверка patch и diff |
| POST | `/api/clusters/:clusterId/config/:node/apply` | Применение утверждённого плана |
| GET | `/api/clusters/:clusterId/config/:node/history` | История ревизий |
| GET | `/api/clusters/:clusterId/config/:node/history/:id` | Очищенная ревизия |
| POST | `/api/clusters/:clusterId/config/:node/restore-plan` | Preview восстановления |
| POST | `/api/clusters/:clusterId/config/:node/restore` | Восстановление утверждённого плана |

Типы: `talos-upgrade`, `kubernetes-upgrade`, `rolling-reboot`.
Создание принимает `kind`, `version` (кроме reboot), `allowDowntime`
и `confirmedCluster`. Acknowledge принимает `{"reviewed": true}`.

Автоматические тесты используют тестовые клиенты; они не заменяют проверку
обновления и восстановления на отдельном стенде. Снимок etcd не содержит
данные приложений с persistent volumes.
