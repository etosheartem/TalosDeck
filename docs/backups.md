# Резервные копии и восстановление

Все настройки и каталоги привязаны к выбранному кластеру. Создание копии,
восстановление и диагностика выполняются через сохраняемые задания.
Закрытие вкладки не прерывает операцию. После аварийного завершения TalosDeck
задание получает `interrupted`: сначала проверьте инфраструктуру, затем подтвердите
review в журнале. Команда автоматически не повторяется.

## Что сохраняется

- **etcd**: снимок Kubernetes API state с SHA-256.
- **full**: etcd, machine configurations, talosconfig и metadata в tar.gz.

Обе разновидности могут содержать высокопривилегированные секреты. Скачивание,
удаление, настройка targets и восстановление доступны только Administrator.
Operator может создавать копии и читать журнал; Viewer видит каталог.
Backup данных PVC — отдельная задача: etcd сохраняет описания томов, но не их содержимое.

## Local, S3 и MinIO

В разделе **Backups → Targets** создайте S3 target: endpoint, bucket, region,
prefix и отдельные access/secret keys. Bucket должен существовать. HTTPS
проверяет сертификат; HTTP разрешён для явно выбранного локального endpoint.
Для частного CA настройте доверие контейнера, не отключайте TLS-проверку.

Credentials шифруются в SQLite и не возвращаются API. Пустые поля ключей при
редактировании сохраняют прежние значения. Endpoint/bucket/prefix target,
уже содержащего копии, нельзя заменить: создайте новый target, чтобы старые
restore points оставались доступны. Объекты размещаются под prefix/cluster-ID.

Задание сначала создаёт и проверяет локальную копию, затем отправляет её в S3.
Ошибка отправки оставляет локальную копию и отмечает задание как failed.
Если часть MachineConfig недоступна, архив помечается `partial`, а задание
завершается ошибкой даже после выгрузки. Такая копия не запускает retention
и не заменяет последнюю полную копию при проверке здоровья backup.
При скачивании удалённой копии проверяются размер и полный SHA-256; ETag
не используется вместо контрольной суммы. Локальный каталог должен иметь
достаточно места для создания архива и временного файла восстановления.

**Schedule** задаёт интервал в часах, retention и target. Настройки и следующее
время запуска сохраняются в registry. После restart просроченный запуск
ставится в очередь один раз; несколько пропущенных интервалов не создают
пачку одинаковых копий. Конфликтующая операция задерживает запуск.
Retention применяется после успешного создания/выгрузки: отдельно сохраняются
последние N полных локальных копий и N полных удалённых копий для каждого target.
Локальная копия после сбоя выгрузки не вытесняет успешную удалённую копию.
Partial-архивы в эту квоту не входят и автоматически не удаляются.
Ошибка удаления видна в job.
Не используйте тот же S3 prefix для внешнего удаления объектов без согласования
с каталогом TalosDeck. Telegram сообщает итог jobs, если уведомления настроены.

## Подготовка восстановления

Держите вне управляемого кластера:

1. Full backup и независимую копию registry TalosDeck.
2. Keyring TalosDeck отдельно от registry.
3. Исходные Talos secrets/machine configurations и административный talosconfig.
4. Образы нужной версии Talos и резервные копии данных приложений.

Встроенное восстановление предназначено для **того же кластера**, исходных
control-plane адресов и версий Talos. Оно сохраняет STATE и текущие machine
configurations. Перенос на другие машины или восстановление при утрате Talos
credentials требует ручной подготовки по [официальной процедуре Talos](https://docs.siderolabs.com/talos/v1.13/build-and-extend-talos/cluster-operations-and-maintenance/disaster-recovery).
Самостоятельно подменять talosconfig другим кластером нельзя.

## Восстановление через интерфейс

Выберите backup и откройте Restore. Сервер проверит checksum архива, внутренний
hash и структуру базы etcd, исходные версии и разметку каждой control-plane ноды. План действует
30 минут, привязан к автору и используется один раз. Введите имя кластера.

После запуска:

1. Повторно проверяются backup и выбранные control planes.
2. На каждой control plane очищается только раздел с etcd: ETCD при отдельном
   разделе либо EPHEMERAL при прежней разметке. STATE и пользовательские диски
   не очищаются. EPHEMERAL может содержать и другие локальные данные ноды.
3. Все etcd services должны перейти в Preparing.
4. Одна нода выполняет `talosctl bootstrap --recover-from` с проверенным snapshot.
5. Перезапускается kubelet на workers: это сбрасывает watches старого etcd state.
6. Проверяются etcd health, новые kubelet leases, Ready нод и стабильность
   control-plane компонентов в течение 30 секунд. Статусы из snapshot сами
   по себе не считаются подтверждением восстановления.

Перезапуск worker kubelets также предусмотрен в
[процедуре восстановления Sidero](https://docs.siderolabs.com/omni/cluster-management/restore-etcd-of-a-cluster-managed-by-cluster-templates).

После начала очистки Stop не оставляет половину quorum в старом состоянии:
критический этап восстановления должен закончиться. При потере процесса
задание остаётся interrupted и требует ручной проверки. Kubernetes API
недоступен во время восстановления; API state после времени snapshot теряется.

Проверьте namespaces, Deployments, StatefulSets, Secrets приложения и реальные
данные томов после восстановления. Успешный etcd restore не доказывает
целостность PVC. Время восстановления зависит от размера snapshot, скорости
перезагрузки, числа control planes и скачивания образов; проведите тренировку
на собственной конфигурации и запишите фактические RPO/RTO.

## Диагностика

**Diagnostics → Run** проверяет Talos/services, etcd, Kubernetes nodes,
pressure, system workloads/CNI, pods, PV/PVC, события и давность backup.
Частичная ошибка оставляет уже собранные результаты. Support bundle содержит
только сформированные health findings; raw logs, конфигурации, Secret objects,
ключи, токены и произвольные event messages в него не включаются. Имена нод,
ресурсов и внутренние адреса остаются для диагностики.
