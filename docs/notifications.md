# Уведомления

Alert Center хранит состояние проблемы отдельно от доставки. Отключённый канал или ошибка получателя не означают, что проблема разрешена. Подтверждение/тишина также не исправляют инфраструктуру.

Новый канал сам по себе не должен запускать рассылку: настройте получателя, включите канал и создайте маршрут нужной серьёзности. Для проверки используйте явное действие отправки теста. Оно отправляет настоящее сообщение указанному получателю.

## Каналы

| Тип | Поля конфигурации | Передача |
|---|---|---|
| Telegram | `token`, `chatId` | HTTPS Bot API, простой текст без parse mode |
| Slack | `url` | Incoming webhook; markdown и раскрытие mentions отключены |
| Discord | `url` | Webhook; `allowed_mentions.parse=[]` |
| Webhook | `url`, необязательный `hmacSecret` | POST JSON со стабильным `eventId` |
| Email | `smtpHost`, `smtpPort`, `smtpTLS`, `smtpFrom`, `smtpTo`; необязательная пара `smtpUsername`/`smtpPassword` | `smtpTLS=tls` либо `starttls`, проверка серверного сертификата обязательна |

`SMTPTo` в JSON называется `smtpTo`: список адресов через запятую, максимум 20. Для SMTP порты задаются явно. STARTTLS без поддержки TLS сервером завершается ошибкой; понижения до plaintext нет. Заголовки письма фиксированы, текст кодируется в base64, вложений нет.

Webhook URL по умолчанию требует HTTPS. `allowHTTP="true"` разрешает явно выбранную администратором HTTP-интеграцию; используйте только в доверенной сети. Userinfo и fragment в URL запрещены. Redirects не выполняются, поэтому секрет из URL не пересылается другому получателю. Пользовательские webhook URLs могут содержать секрет в пути — не публикуйте их.

## Generic webhook

Тело содержит `eventId`, `clusterId`, `alertId`, `state`, `severity`, `title`, `details`, `node`, `ruleId`, `occurredAt`. Получатель должен дедуплицировать запросы по `eventId`: после сетевого сбоя невозможно всегда определить, получил ли он сообщение.

Заголовки:

```text
X-TalosDeck-Event-ID: <eventId>
X-TalosDeck-Timestamp: <Unix seconds>
X-TalosDeck-Signature: sha256=<hex HMAC>
```

Подпись присутствует только при настройке `hmacSecret`. Алгоритм: HMAC-SHA256 от точных байтов `timestamp + "." + requestBody`. Проверяйте подпись сравнением за постоянное время и ограничивайте возраст timestamp, например пятью минутами; храните обработанные event IDs. При повторной отправке timestamp и подпись могут измениться, event ID остаётся идентификатором события.

## Ограничения и ошибки

Одна попытка ограничена 20 секундами. Текст ограничен по размеру; произвольные логи, конфигурации и вложения не отправляются. Ответ HTTP читается максимум до 64 KiB и не копируется в журнал ошибок. HTTP 429 может задать `Retry-After` в секундах, максимум один час. Повторы организует outbox, а не транспорт.

`uncertain` означает, что транспорт не смог подтвердить результат после возможной отправки. Ручной повтор может создать дубликат у получателя. HTTP redirect считается отказом. Для Telegram дополнительно проверяется `ok=true`; для SMTP успешная доставка означает подтверждение SMTP-сервером, а не прочтение письма или попадание во входящие.

Секреты получателей хранятся через encrypted configuration хранилище и не возвращаются в public channel DTO. Транспорт возвращает фиксированные сообщения ошибок без server response, credentials и URL. Его входной текст должен быть безопасной сводкой Alert Center: транспорт не является универсальным очистителем произвольных секретов в тексте.

Автотесты используют только локальные HTTP/SMTP/TLS fixtures. Они не отправляют сообщения настоящим Telegram/Slack/Discord/email получателям.

## Состояние и маршруты

В **Наблюдение → Алерты** доступны активные и разрешённые проблемы, важность,
нода, время появления и последней проверки. Недоступность источника помечает
предыдущие наблюдения как stale, а не как исправленные. После перезапуска
нужен новый успешный опрос. CPU, память и заполнение диска вызывают предупреждение
при двух измерениях от 90%; восстановление — ниже 85%. Также проверяются
готовность нод, etcd, Kubernetes pressure, сертификаты и наличие полной копии
за последние 24 часа. Прерванное задание остаётся активной проблемой до проверки
оператором; завершения заданий сохраняются как отдельные события.

Администратор задаёт каналы и маршруты в **Настройки кластера → Уведомления**.
Маршрут выбирает минимальную важность, rule IDs, ноды и каналы, восстановление
и интервал напоминаний. Получатель-пользователь — привязка канала к существующему
активному пользователю; она не фильтрует события по автору задания.
Настройки и outbox принадлежат выбранному кластеру. Задания создания новых
кластеров на уровне платформы пока фиксируются в заданиях и аудите без этих маршрутов.

Viewer читает алерты. Operator дополнительно управляет временной тишиной
и читает журнал доставки. Только Administrator меняет каналы/маршруты,
отправляет тесты и повторяет доставку. Тишина ограничена временем и фильтром;
она откладывает отправку, но не меняет состояние проблемы.

Существующая Telegram-конфигурация мигрирует один раз при открытии кластера.
Старый отправитель отключается; старые `/alerts/config` и `/alerts/test`
возвращают 410, используйте `/notifications/channels` и тест выбранного канала.
Секреты канала доступны только на запись: пустой `config` при редактировании
сохраняет прежнюю конфигурацию целиком, непустой заменяет её целиком.
`generation` канала и `revision` маршрутов предотвращают потерю параллельных правок.

## Надёжность доставки

Состояние события и очередь сохраняются одной зашифрованной записью до отправки.
Повторные опросы и перезапуски не создают повтор одной и той же смены состояния.
Очередь проверяет актуальность события, маршрута, тишины и поколения канала.
Изменение получателя подавляет уже подготовленные отправки старому получателю.
Подтверждённые отказы повторяются до пяти попыток; неопределённый исход
требует ручного решения. Доставка с результатом `sent` подтверждает приём
транспортом, но не прочтение человеком. Хранение ограничено; журнал не является
бессрочным архивом всех сообщений.
